## 2. Что делать дальше — очередь работ

Ничего из нижеперечисленного не выбрано пользователем как обязательное к
немедленному старту — это **меню с рекомендованным порядком**, спроси пользователя,
что из этого приоритетно, если это не указано в его сообщении.

### 2.1 Можно начинать прямо сейчас, чистым кодом, без внешних аккаунтов
Рекомендуемый порядок внутри этой группы:
1. **`docs/STORE_LAUNCH_TZ.md` §10 (тесты звонков/push/upload backend)** — самый
   ценный пробел: именно в зоне звонков/push исторически больше всего
   постфактум-багфиксов (см. журнал `CLAUDE.md`). Нужен мок socket.io для
   `socketServer.js` `call:*`, мок `web-push`, мок S3-клиента для presign-флоу.
2. **`docs/STORE_LAUNCH_TZ.md` §13 (остаток) — admin CSP unsafe-inline** — вынести
   48 инлайн-`onclick` в `backend/public/admin/{admin.js,index.html}` на
   `addEventListener`, убрать `unsafe-inline` из CSP. Требует полного
   клик-тестирования всей админки руками (все кнопки/формы), поэтому раньше было
   отложено — не мелкая задача, несмотря на P2.
3. **`docs/STORE_LAUNCH_TZ.md` §15 — maskable-иконка safe zone** — быстрая
   проверка в maskable.app + при необходимости отдельный файл иконки с отступом.
4. Из `TZ_IMPROVEMENTS.md`, если пользователь захочет функционала, а не только
   security/store-подготовку: D4 (архив чатов) и D1 (статус «Доставлено») —
   вероятно наиболее ощутимая для пользователей ценность при разумном объёме.
   E2 (double-tap реакции) — маленькая, приятная фича.

### 2.2 Требует решения/аккаунта пользователя, но код можно готовить заранее
- **§6 Sentry** — нужен бесплатный аккаунт на sentry.io + DSN. Можно сразу спросить
  пользователя, готов ли он завести аккаунт (или дать существующий DSN), и
  реализовать интеграцию (backend `Sentry.init` + `errorHandler`, frontend
  `main.tsx` + связка с `ErrorBoundary`) сразу после получения DSN.
- **§3.1 Android TWA** — нужен Google Play Console ($25 разово) + keystore.
  Технически: Bubblewrap CLI/PWABuilder вокруг существующего манифеста PWA,
  `.well-known/assetlinks.json` на прод-домене. Рекомендованный **первый шаг**
  из раздела 3 всего мастер-плана (дешевле и быстрее iOS).
- **§11 Резервный TURN-провайдер** — managed-провайдер (например Metered,
  упоминался в истории проекта), может быть платным. Логично делать рядом с
  публикацией под реальных пользователей (Этап 5 по плану), не раньше.
- **§3.2 iOS Capacitor** — Apple Developer ($99/год) + Mac для сборки. Самый
  дорогой и рискованный путь (APNs вместо Web Push для звонков — отдельная ветка
  на бэкенде). Начинать после того, как Android-путь обкатан.
- **§12 QA-чеклист на реальных устройствах** — процесс, не разовая задача;
  прогонять перед каждой подачей в стор, начиная с публикации под Android.

### 2.3 Бэклог — не по графику, а по сигналу от роста аудитории/нагрузки
- **§16 Redis-адаптер** (`docs/REDIS_SCALING_TZ.md`, 0% реализовано) — при
  реальной боли от одного процесса/обрыва сокетов при деплое.
- **§17 Admin Panel v2** (`docs/ADMIN_PANEL_TZ.md`, 0% реализовано) — можно
  раньше по времени (не зависит от других этапов); раздел «Call success rate»
  оттуда полезно поднять пораньше — объективно измерить эффект §11.
- **F1 групповые звонки (TZ_IMPROVEMENTS.md)** — крупный отдельный проект
  (mediasoup SFU), делать только когда/если появится явный запрос пользователей.

## 3. Методология работы в этом репозитории

Это конспект того, что уже подробно расписано в шапке и хвосте `CLAUDE.md` —
здесь специально продублировано и заострено, чтобы агент с чистой памятью не
пропустил, даже если решит не читать `CLAUDE.md` построчно целиком (хотя должен).

### 3.1 Перед началом любой задачи
1. Прочитать `CLAUDE.md` целиком (структура, конвенции, таблица «Типовые задачи»,
   журнал изменений — свежие записи сверху). Не сканировать репозиторий заново,
   если карта уже отвечает на вопрос «где искать».
2. Если задача — развитие функциональности: свериться с `ROADMAP.md` (сейчас
   полностью пуст по открытым пунктам, но там же — принципы качества и
   архитектура deep-links, актуальные при добавлении новых действий).
3. Если задача — из store-launch плана: прочитать **весь** релевантный раздел
   `docs/STORE_LAUNCH_TZ.md` целиком (там есть нюансы формулировок задним числом),
   потом только — файлы по ссылкам из него.
4. Если задача явно не описана ни в одном ТЗ — уточнить объём у пользователя,
   не гадать.

### 3.2 Во время работы
- Изменение схемы БД — только новый файл-миграция в `backend/src/db/versions/NNN_*.js`
  (идемпотентно, применяется автоматически при старте). Никогда не редактировать
  старые миграции задним числом.
- Новая таблица/колонка со ссылкой на `users(id)`: если сущность должна пережить
  удаление автора (видна другим участникам — сообщение, звонок, заметка) —
  переносить на `userService.DELETED_ACCOUNT_USER_ID` при `deleteAccount()`, НЕ
  просто `ON DELETE CASCADE`. Если сущность приватная — обычный `CASCADE`/`SET NULL`
  в самой схеме подходит. `PRAGMA foreign_keys=ON` включён всегда — забытая FK-связь
  без стратегии удаления сломает `deleteAccount()` при первом же живом пользователе.
- Сообщения шифруются at-rest (AES-GCM) — НИКОГДА не писать открытый текст в БД
  (даже временно/для дебага). Поиск — только через blind-index (`utils/searchIndex.js`).
- Дизайн — токены из `web/src/styles/01-tokens-auth-layout.css`, новые точечные
  правки — в финальный слой `18-aurora-overrides.css` (должен оставаться последним
  `@import` в `app.css`). Не хардкодить цвета, не возвращать старый синий `#2f81f7`.
- Секреты — только в env (Amvera/Vercel), никогда в коде/`VITE_*` (репозиторий
  публичный, `VITE_*`-переменные попадают в открытый бандл).
- i18n (если задача касается текста): любой НОВЫЙ пользовательский текст на фронте
  — сразу в оба неймспейса `web/src/i18n/locales/{ru,en}/<namespace>.json`, не
  хардкодить русский с расчётом «переведу потом». Backend-текст с известным
  получателем (email/push) — через `backend/src/i18n/index.js` (`t(lang, key, params)`),
  а не хардкод.

### 3.3 Перед завершением задачи — обязательный гейт
1. **Backend:** `cd backend && npm test` — все тесты должны быть зелёными
   (сейчас 173). Если меняется поведение — добавить/обновить тест в
   `backend/tests/` (файл `smoke.test.js` — основной, `i18n.test.js` — i18n-специфичный,
   новые тематические файлы можно добавлять отдельно, не забыть дописать путь к
   ним в `"test"` скрипте `backend/package.json`, glob `tests/` там не работает
   на этой Node/Windows-связке — пути нужно перечислять явно).
2. **Frontend:** `cd web && npm run build` (strict tsc + vite) — обязательна перед
   любым пушем, ловит ошибки типов. `cd web && npm test` (vitest) — если менялась
   логика фронта.
3. **Визуальная проверка** (если менялся UI): использовать `preview_start`/
   `preview_*`-инструменты (НЕ голый `Bash`/терминал для дев-сервера) — поднять
   backend+web, залогиниться реальным тестовым аккаунтом (создать через
   регистрацию, если нет), проверить экран в браузере (`preview_screenshot`/
   `preview_snapshot`), а не только полагаться на успешную сборку. Для труднодостижимых
   состояний (нужен групповой чат / реальный WebRTC-звонок / сбой сети) —
   допустимо ограничиться статической проверкой (grep + успешная сборка/тесты) с
   явной пометкой в журнале, почему живая проверка пропущена — это устоявшийся
   паттерн в истории проекта, не импровизировать новый.
4. **Журнал `CLAUDE.md`** — одна новая запись сверху (формат: `ДАТА | область |
   что сделано (+ детали, найденные баги, как проверено)`). Если структура
   проекта изменилась (новая папка/стор/роут) — обновить и соответствующий раздел
   карты выше в файле, не только журнал. Если журнал разросся за ~40 строк —
   свернуть самые старые записи в одну строку-сводку (см. правило в хвосте
   `CLAUDE.md`).
5. **Статус в самом ТЗ-документе** (если работа из `docs/STORE_LAUNCH_TZ.md` или
   аналогичного) — отметить раздел как `✅ РЕАЛИЗОВАНО (дата, коммит)` прямо
   внутри документа, с кратким резюме что сделано и как проверено (по образцу уже
   существующих отметок в файле).
6. **Коммит** — по существующему стилю проекта (`git log` покажет паттерн:
   `feat(area): краткое описание` на русском в теле, английский only в
   служебных префиксах). Один коммит — одна логическая волна работы.
7. **Push в `devDK`** — только если пользователь просил push по ходу работы
   (было явно так в последней сессии — «продолжай и по ходу завершения каждой
   волны — пуш в devDK»). Если явной команды нет в новой сессии — спросить или
   ограничиться коммитом, push — по запросу (см. общее правило «спрашивать перед
   действиями с широким блэст-радиусом», хотя пуш в рабочую ветку `devDK`, не в
   `main`, обычно низкого риска).

### 3.4 Общие принципы (уже есть в CLAUDE.md, не изобретать заново)
- Не хардкодить то, что уже параметризовано (акцент, тема, язык, фон).
- Переиспользовать существующие компоненты/паттерны раньше, чем писать новые
  (модалки → `modalOverlay`/`modalCard`; плееры → `chat/messageBubble/*`; toggle →
  `ui/Toggle`; ввод — `chat/Composer`, параметризуется колбэками).
- Не переусложнять: три похожие строки лучше преждевременной абстракции; не
  добавлять функциональность/обработку ошибок «на всякий случай» сверх того, что
  реально нужно для задачи.
- Комментарии — только там, где неочевидна ПРИЧИНА (скрытое ограничение,
  обходной путь конкретного бага, неочевидный инвариант), не пересказ того, что
  и так ясно из кода.
