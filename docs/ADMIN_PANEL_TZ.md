# ТЗ: панель контроля и аналитики приложения (admin v2)

> Статус: **БЭКЛОГ к реализации.** Отдельная крупная задача. Цель — превратить
> текущую базовую админку в полноценную панель наблюдаемости: удержание,
> использование функций, что сбоит, что стабильно — чтобы принимать решения по
> развитию на данных, а не на ощущениях.

## 1. Что есть сейчас

- Бэкенд: `routes/admin/*` (sub-routers) — `stats`, `users`, `chats`,
  `moderation`, `stickerRepair`, `diagnostics` (ошибки/аудит/бэкап). Гейт:
  логин + JWT 12ч + единственный admin по `ADMIN_USERNAME`.
- Фронт: `public/admin/` — статический HTML/JS на Bootstrap.
- Метрик использования/удержания/надёжности по фичам **нет** — только базовые
  счётчики и списки.

## 2. Цель

Видеть «абсолютно всё» и работать с этим:
1. **Удержание** — возвращаются ли пользователи (DAU/WAU/MAU, retention-когорты,
   живут ли ЗАКРЫТЫЕ круги — для «мои близкие» это ключевая метрика).
2. **Использование функций** — какие фичи используют часто, какие почти нет
   (звонки, медиа, коллекции, «Вопрос дня», стикеры, ассистенты, опросы…).
3. **Что сбоит** — частота ошибок/неудач по фичам (особенно **успех звонков**,
   доставка сообщений, загрузка файлов, push).
4. **Что стабильно** — тренды надёжности во времени, чтобы ловить регрессии.

## 3. Архитектура: сбор событий (фундамент)

Без инструментирования метрик не будет. Вводим лёгкий event-трекинг.

### 3.1 Таблица событий (новая миграция)
```sql
CREATE TABLE analytics_events (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  ts         INTEGER NOT NULL,           -- Date.now()
  user_id    TEXT,                       -- кто (NULL для системных)
  event      TEXT NOT NULL,              -- 'call.attempt' | 'call.connected' | 'message.sent' | 'upload.ok' | 'feature.open' ...
  props      TEXT,                       -- JSON: {callType, durationMs, errorCode, feature, ...} — БЕЗ контента/PII
  session_id TEXT
);
CREATE INDEX idx_ae_ts    ON analytics_events(ts);
CREATE INDEX idx_ae_event ON analytics_events(event, ts);
CREATE INDEX idx_ae_user  ON analytics_events(user_id, ts);
```

### 3.2 Принципы
- **Никакого контента/PII**: не логируем текст сообщений, имена файлов, телефоны.
  Только тип события + технические props (тип звонка, код ошибки, длительность).
- **Сервер — источник правды** для серверных событий; клиент шлёт только то, что
  виден только ему (напр. `call.ice_failed`, `feature.open`) через лёгкий
  `POST /events` (батч, rate-limit).
- **Ретенция/объём**: чистка событий старше N дней (cron/worker), либо
  предагрегация в суточные сводки (`analytics_daily`) + дроп сырых.

### 3.3 Ключевые события для инструментирования
| Область | События |
|---|---|
| **Звонки** | `call.attempt`, `call.ring`, `call.accepted`, `call.connected`, `call.failed{reason}`, `call.ended{durationMs}`, `call.ice_relay_used{bool}` |
| Сообщения | `message.sent{hasAttachment}`, `message.delivered`, `message.push_sent/push_fail` |
| Загрузки | `upload.ok{type,bytes}`, `upload.fail{stage}` |
| Фичи | `feature.open{name}` (collections/daily-prompt/assistant/notes/stickers/polls) |
| Сессии | `session.start`, `app.foreground` (для DAU и presence-качества) |
| Ошибки | `error{area,code}` (уже есть лог ошибок — связать) |

## 4. Дашборды (фронт admin v2)

### 4.1 Обзор (главная)
- DAU / WAU / MAU + спарклайны; новые регистрации/день.
- «Здоровье» в реальном времени: онлайн сейчас, активные звонки, ошибки за час.

### 4.2 Удержание
- Retention-когорты (N1/N7/N30 по неделям регистрации) — таблица-«heatmap».
- **Удержание закрытых кругов**: доля групп/ЛС, активных через 1/2/4 недели
  (главная метрика продукта).
- % ответов на «Вопрос дня» (engagement-ритуал).

### 4.3 Использование функций
- Топ фич по уникальным пользователям/неделя; тренды; «мёртвые» фичи.
- Воронки (напр. открыл коллекции → создал папку → загрузил файл).

### 4.4 Надёжность (что сбоит)
- **Call success rate** = `call.connected / call.attempt` (общий и по сетям/типам),
  доля звонков через relay, причины `call.failed`. ← прямо отвечает на текущую боль.
- Upload success rate; push success rate; message delivery latency.
- Тренды ошибок по областям; алёрты при просадке.

### 4.5 Пользователи / Чаты / Модерация
- Расширить существующие разделы: поиск, карточка пользователя (его события,
  устройства/сессии, активность), жалобы, действия (бан/сброс/удаление — есть).

## 5. Бэкенд: новые эндпоинты (под admin-гейтом)
- `GET /admin/api/analytics/overview?range=` → DAU/WAU/MAU, health.
- `GET /admin/api/analytics/retention?cohort=` → когорты.
- `GET /admin/api/analytics/features?range=` → использование.
- `GET /admin/api/analytics/reliability?range=` → success-rates, ошибки.
- Все — агрегации по `analytics_events`/`analytics_daily` (готовить индексы; тяжёлые
  запросы кэшировать на 1–5 мин).
- `POST /events` (клиентские события, батч, rate-limit, валидация whitelisted-имён).

## 6. Этапы внедрения
1. **Сбор**: миграция `analytics_events` + хелпер `track(event, props, userId)` +
   инструментирование звонков и сообщений (самое ценное сразу).
2. **Reliability-дашборд**: call success rate + ошибки (отвечает на текущую боль).
3. **Удержание**: DAU/WAU/MAU + когорты + активность кругов.
4. **Использование функций** + воронки.
5. **Предагрегация** `analytics_daily` + чистка сырых событий (объём/приватность).

## 7. Нюансы и риски
- **Приватность** — публичный репозиторий + шифрование как ценность: метрики
  должны быть строго обезличены (никакого контента). Документировать, что собираем.
- **Объём** на одном SQLite: события растут быстро → обязательна предагрегация и
  ретенция (§3.2). При большом объёме — выносить аналитику в отдельную БД/таблицу.
- **Производительность**: запись событий не должна тормозить горячие пути
  (батчинг/асинхронная вставка; не блокировать отправку сообщения/звонок).
- **Нагрузка на админку** — тяжёлые агрегаты кэшировать, не считать на каждый клик.

## 8. Критерии приёмки
- Видно DAU/WAU/MAU и retention-когорты на реальных данных.
- Виден **call success rate** и причины неудач (можно отследить эффект починки TURN).
- Видно, какие фичи используются, а какие — нет.
- Сбор событий не содержит контента/PII и не замедляет приложение.
