## 1. [P0] Privacy Policy, Terms of Service, согласие при регистрации

**Статус:** не существует. Grep по всему репозиторию не находит ни страницы,
ни ссылки, ни чекбокса согласия. `web/src/components/auth/RegisterForm.tsx`
собирает только username/email/пароль.

**Проблема.** Оба стора **обязательно** требуют публичный URL политики
конфиденциальности при подаче карточки (Apple — в App Store Connect, Google —
в Data Safety форме и в самом листинге). Без него заявку не примут даже на
ревью. Плюс это база для остальных пунктов (жалобы, экспорт данных, ИИ-фичи)
— без документа не на что сослаться.

**Объём работ:**
1. Текст политики конфиденциальности — честно описать, что реально
   происходит в коде (не шаблон из интернета):
   - Какие данные собираются: username, email, display_name, bio, дата
     рождения (опционально, `hide_birth_date`), аватар, статус/presence,
     история чатов (зашифрована at-rest AES-GCM ключом сервера — **это НЕ
     end-to-end шифрование**, сервер технически может расшифровать; это
     нужно явно и честно написать, иначе — риск претензии за вводящее в
     заблуждение заявление о «приватности»).
   - Кто получает данные: S3-провайдер (Yandex Cloud) для медиа, email-провайдер
     для писем (сброс пароля, поддержка), **Groq** как сторонний LLM-процессор
     для ассистентов (`backend/src/services/assistantService.js`,
     `dataAssistantService.js` — этап D строго opt-in, это плюс, но раскрыть
     обязательно), **Giphy API** для GIF (`backend/src/routes/gif.js`).
   - Как удалить данные: `DELETE /users/me` (self-service) + `/export/my-data`
     (GDPR-экспорт) — уже реализовано, только описать словами для юзера.
   - Хранение бэкапов (зашифрованы AES-256-GCM в S3, `utils/backupCrypto.js`).
2. Terms of Service — минимально: возрастной порог (рекомендация: 16+, чтобы
   не попадать под полный COPPA-режим США; если ЦА — семьи, честно
   зафиксировать, что аккаунт до 13/16 лет заводится с согласия родителя),
   правила поведения (что нельзя — спам/угрозы/незаконный контент), что
   бывает при нарушении (блокировка/удаление аккаунта — механизм уже есть в
   admin-панели).
3. Разместить как статические страницы фронта: `web/src/components/legal/`
   (или простые статические HTML на Vercel + отдельный роут `/privacy`,
   `/terms` — не требует бэкенда, доступны без авторизации, именно на них
   должны ссылаться сторы).
4. В `RegisterForm.tsx` — чекбокс «Я принимаю [Политику конфиденциальности] и
   [Условия использования]», обязательный для отправки формы (аналогично
   существующим клиентским проверкам `emailValid`/`ready`).
5. Ссылки на обе страницы — в футере `AuthScreen.tsx` и в
   `ProfileSettingsModal.tsx` (пункт «О приложении»/юридическая информация).

**Критерии приёмки:**
- Обе страницы доступны по прямому URL без авторизации.
- Регистрация невозможна без отметки чекбокса.
- В политике конфиденциальности прямо названы: Yandex S3, email-провайдер,
  Groq (LLM), Giphy — как получатели/обработчики данных.
- Формулировка про шифрование сообщений не заявляет E2E там, где его нет.

## 3. [P0] Нативная обёртка: TWA (Android) + Capacitor (iOS)

**Статус:** отсутствует полностью. Проверено: нет `capacitor.config.*`, нет
`android/`/`ios/`, нет зависимостей Capacitor/Cordova/Expo/React Native ни в
`web/package.json`, ни где-либо в репозитории. Есть только корректный PWA
(`vite-plugin-pwa`, `web/src/sw.ts`, манифест в `vite.config.ts:14-33`).

**Проблема.** Без артефакта под конкретную платформу подавать в сторы
физически нечего — это не вопрос доработки кода, а отдельный build-pipeline.
Пути для Android и iOS принципиально разные по трудозатратам и рискам.

### 3.1 Android — TWA (Trusted Web Activity), рекомендуемый первый шаг

Google официально поддерживает публикацию PWA как обёрнутого TWA — это
быстрее и дешевле, чем полноценная нативная разработка.

**Объём работ:**
- Инструмент: [Bubblewrap CLI](https://github.com/GoogleChromeLabs/bubblewrap)
  или PWABuilder — генерирует Android-проект вокруг существующего манифеста.
- Обязательное условие: **Digital Asset Links** — файл
  `.well-known/assetlinks.json` на домене прод-фронта (Vercel), подтверждающий
  владение доменом связкой с SHA-256 отпечатком подписи APK/AAB — иначе TWA
  покажет браузерную строку URL сверху (провал «нативного» вида).
  Разместить статикой в `web/public/.well-known/assetlinks.json`.
- Манифест (`vite.config.ts:17-35`) уже содержит нужные поля (`name`,
  `icons`, `display: 'standalone'`, `start_url`) — переиспользуется как есть.

**Критерии приёмки:** установленное из Play Store (внутренний тест-трек)
приложение открывается без видимой браузерной строки URL, push работает,

### 3.2 iOS — Capacitor, более трудоёмкий и рискованный путь

Apple не признаёт TWA-аналог; исторически отклоняет «сайт в вебвью» по
Guideline 4.2 (Minimum Functionality) без ощутимой нативности.

**Объём работ:**
- `npm install @capacitor/core @capacitor/ios`, `npx cap init`, `npx cap add
  ios` — обернуть уже собранный `web/dist` (или указать `server.url` на прод
  для быстрого старта, но для финального релиза Apple предпочитает
  бандлить статику внутрь ipa, а не грузить с внешнего сервера как основной
  режим — сетевые вызовы к API/сокетам остаются, это ок, но начальный HTML/JS
  должен идти из бандла).
- Полностью убрать любой намёк на browser chrome — Capacitor по умолчанию
  это делает, но перепроверить статус-бар/safe-area (`viewport-fit=cover` +
  CSS `env(safe-area-inset-*)` — сейчас не проверено, вероятно отсутствует
  под «чёлку»/Dynamic Island, добавить в `web/index.html`/базовые стили).
- Камера/микрофон для звонков и видео-кружков: в WKWebView `getUserMedia`
  работает, но **обязательно** нужны ключи `NSCameraUsageDescription` /
  `NSMicrophoneUsageDescription` в `Info.plist`, иначе мгновенный краш при
  первом запросе разрешения.
- Push-уведомления — **это самый большой риск.** WKWebView не имеет доступа к
  Web Push так, как в Safari PWA. Для iOS-приложения из App Store нужен
  `@capacitor/push-notifications` (APNs) — это отдельная ветка на бэкенде:
  `backend/src/utils/webPush.js`/`pushService.js` умеет только Web Push
  (VAPID); нужен параллельный APNs-путь (сертификат/ключ Apple Push, отправка
  через `node-apn` или APNs HTTP/2 API) для звонков и сообщений на iOS-сборке.
  Учитывая, что вся история звонков в журнале завязана на надёжность push
  («входящий звонок доходит через push»), это критично не упростить.
- Sign in with Apple — **не требуется**: приложение не предлагает сторонние
  OAuth-логины (только пароль + passkeys), поэтому правило 4.8 не триггерится.
  Если когда-либо добавится «вход через Google» — тогда придётся добавить и
  Apple.
- App Store Review Guidelines 5.1.1(v) — **уже выполнено**: `DELETE
  /users/me` даёт полное самостоятельное удаление аккаунта (доработать
  повторным подтверждением — раздел 5).
- TestFlight — прогнать реальный бета-цикл перед публичным релизом.

**Критерии приёмки:** IPA проходит внутренний TestFlight-билд, входящий
звонок доставляется push-уведомлением на реальном iPhone при свёрнутом
приложении, камера/микрофон запрашиваются с понятным описанием, нет видимого
browser chrome, safe-area учтена на всех экранах с notch/Dynamic Island.

**Решение, которое нужно принять до старта:** с чего начинать — только
Android (TWA, дни-недели) с последующим iOS, или сразу оба параллельно через
Capacitor (дольше, но один цикл разработки на обе платформы вместо TWA +
отдельный Capacitor-iOS). Рекомендация: **TWA на Android первым** — даёт
работающий стор-листинг быстро и дёшево, вскрывает реальные проблемы (push,
deep-links, safe-area) на более простой платформе, прежде чем вкладываться в
более тяжёлый и рискованный iOS-путь.

## 5. [P0] Подтверждение при удалении аккаунта

**Статус:** `DELETE /users/me` (`backend/src/routes/users.js:79`) удаляет
аккаунт по одной только валидной сессии — без пароля/TOTP.

**Проблема.** Забытая открытая сессия на чужом/общем устройстве (а ЦА
продукта — семьи, общие компьютеры весьма вероятны) = необратимое удаление
аккаунта одним кликом без дополнительного барьера. Ревьюеры сторов прицельно
тестируют flow удаления аккаунта — отсутствие «are you sure» с
переподтверждением личности выглядит небрежно и по сути является дырой.

**Объём работ:**
- Роут принимает `{ password }` (или TOTP-код, если у пользователя включена
  2FA — переиспользовать `verifyTotp` из `utils/totp.js`) в теле запроса,
  сверяет с `bcrypt.compare` перед вызовом `deleteAccount`.
- Фронт: модалка подтверждения (текст, поле пароля) перед вызовом — там же,
  где сейчас кнопка «Удалить аккаунт» в `ProfileSettingsModal`/приватности.
- Rate-limit на попытки (переиспользовать `otpVerifyLimiter`/аналог) — иначе
  сам confirm-эндпоинт станет вектором брутфорса пароля.

**Критерии приёмки:** удаление аккаунта невозможно без ввода верного пароля
(или TOTP при включённой 2FA); неверный пароль — понятная ошибка, попытки
ограничены лимитом.

**Найдено при живом тестировании на проде (2026-07-03): реальное удаление
аккаунта падало с `Internal server error`.** Причина — `calls.caller_id`/
`callee_id`, `chat_notes.last_edited_by`/`created_by` и
`messages.sender_id` ссылаются на `users(id)` БЕЗ `ON DELETE CASCADE`/
`SET NULL` (`001_initial.js`), а `PRAGMA foreign_keys = ON` включён всегда
(`config/database.js`) — значит это не гипотетический риск, а реальный
баг: воспроизведён на аккаунте, который когда-либо участвовал в звонке,
и в общем случае бьёт любого, кто оставлял заметку в чате или писал в
ГРУППОВОЙ чат, который потом покинул (группа остаётся жить для остальных —
`chats` строка не удаляется, только `chat_members`).

**Полностью исправлено** — заведён постоянный login-less аккаунт-заглушка
**«Удалённый аккаунт»** (`id='deleted-account'`, миграция
`017_deleted_account_ghost.js`, константа
`userService.DELETED_ACCOUNT_USER_ID`). `deleteAccount()`
(`services/chat/teardown.js`) перед `DELETE FROM users` теперь
переносит («усыновляет») все осиротевшие ссылки на этого пользователя:
`messages.sender_id`, `calls.caller_id`/`callee_id`,
`chat_notes.last_edited_by`/`created_by` — **ничего не удаляется и не
зануляется**, вся переписка/история звонков/заметки остаются как есть,
просто автор показывается как «Удалённый аккаунт» (сам по себе — обычная
строка `users`, никакой специальной UI-логики не потребовалось). Заглушка
исключена из поиска пользователей (`searchUsers`). Регресс-тесты
воспроизводят исходную ошибку без фикса (`FOREIGN KEY constraint failed`)
и проходят с ним, плюс отдельный тест на перенос сообщения в живой группе
и на исключение из поиска. Тестовая БД (`backend/tests/smoke.test.js`)
теперь тоже включает `PRAGMA foreign_keys=ON`, как в проде — раньше весь
этот класс багов был невидим тестам.

**Ретеншн для заглушки** (по просьбе пользователя — «чтобы удалённые
аккаунты не засоряли память и ими не могли злоупотреблять»): новый воркер
`workers/deletedAccountCleanup.js` (запуск при старте + раз в 24ч) удаляет
`messages`/`calls`, унаследованные «Удалённым аккаунтом», старше
`DELETED_ACCOUNT_RETENTION_DAYS` (по умолчанию 180 дней; `DEPLOY.md`).
Заметки (`chat_notes`) не чистятся — это справочный контент чата, а не
одноразовый поток сообщений, и объём на порядки меньше. Это единственное
место, где контент реально исчезает — но только контент, унаследованный
безликой заглушкой, спустя долгий срок, а не в момент удаления аккаунта.

Живьём подтверждено на проде: полный цикл (неверный пароль → ошибка,
верный пароль → аккаунт удалён, повторный вход → «Неверный логин или
пароль») прошёл успешно после деплоя фикса.

## 7. [P1] Звонки переживают деплой/рестарт процесса

**Статус:** `activeCalls` — чистый in-memory `Map`
(`backend/src/socket/socketServer.js:32`). CI (`.github/workflows/deploy-amvera.yml`)
деплоит **на каждый push в `devDK`**, что рестартует процесс.

**Проблема.** Любой релиз, попавший на момент активного звонка у
пользователя, молча его обрывает — без `call:ended`, до срабатывания
клиентского peer-gone таймера (секунды тишины, которые выглядят как
зависание). Для мессенджера, где звонкам уже посвящена большая часть журнала
изменений (задержка, TURN, доставка push), это заметная деградация UX сразу
после каждого продакшен-релиза.

**Объём работ (без полного переезда на Redis из раздела 16):**
1. **Минимум:** graceful shutdown — на `SIGTERM` (Amvera шлёт его перед
   убийством) разослать всем участникам активных звонков `call:ending-soon`
   с понятным сообщением («сервер обновляется, звонок будет переустановлен»)
   вместо тихого обрыва; дать клиенту прелюдию до жёсткого дисконнекта
   (несколько секунд).
2. **Лучше:** не деплоить, если есть активные звонки — CI-джоб перед деплоем
   опрашивает health/metrics-эндпоинт (`GET /health` можно расширить полем
   `activeCalls: N`) и либо ждёт (poll с таймаутом), либо явно предупреждает
   в логе деплоя. Компромисс между «блокировать деплой» и «просто уведомить».
3. Долгосрочно — вынести `activeCalls` в Redis (раздел 16) для настоящего
   переживания рестарта без прерывания сигнализации. Не делать сейчас
   отдельно от полного Redis-перехода — усложнение ради половинчатого
   решения того не стоит.

**Критерии приёмки:** тестовый деплой во время активного звонка либо не
рвёт его резко (участники получают понятное сообщение с шансом
переустановить), либо CI осознанно откладывает деплой при непустых звонках.

**✅ РЕАЛИЗОВАНО (2026-07-08) — пункт 1 «минимум», без изменений CI/деплоя
(пользователь явно выбрал не трогать пайплайн — item 2 «лучше» осознанно
пропущен).** `socketServer.js` теперь экспортирует на `io`:
`getActiveCallsCount()` (текущий размер `activeCalls`) и
`notifyCallsEndingSoon(message)` (шлёт `call:ending-soon {callId, message}`
обоим участникам каждого активного звонка — тем же `io.to('user:<id>')`,
что и остальные call-события). `index.js`: `shutdown()` перед началом
разбора сокетов проверяет `io.getActiveCallsCount()` — если есть активные
звонки, вызывает `notifyCallsEndingSoon(...)` и откладывает жёсткий разрыв
на `CALL_SHUTDOWN_GRACE_MS` (env, дефолт 4000мс — заведомо меньше дефолтного
10с окна Docker/Amvera между SIGTERM и SIGKILL) через `setTimeout`, только
затем выполняет прежнюю последовательность (`disconnectSockets` → закрыть
HTTP → закрыть `io` → закрыть БД → `exit`). Если активных звонков нет —
поведение идентично прежнему, без задержки (нет регресса для общего случая).

Фронт: новое событие `call:ending-soon` (подписка в `useSocket.ts`, как и
все остальные call-события) не рвёт звонок сразу — пока звонок ещё активен,
`CallOverlay` показывает баннер с текстом сервера (`endingSoonMessage` в
`useCallStore`). Когда затем реально приходит `call:ended` (из
`disconnectSockets` → уже существующий обработчик `socket.on('disconnect')`,
он не менялся — корректно закрывает звонок и уведомляет второго участника
и без этой правки), фронт показывает не общее «Звонок завершён», а
конкретное «Сервер обновляется — перезвоните» (новое значение `endReason:
'server-restart'`, вычисляется в `useSocket.ts` по наличию
`endingSoonMessage` на момент `call:ended`).

Живая проверка: OS-level SIGTERM невозможно достоверно протестировать на
Windows (libuv на Windows не эмулирует SIGTERM — `process.kill(pid,
'SIGTERM')` вызывает `TerminateProcess`, т.е. жёсткий килл в обход всех
JS-обработчиков; ровно так повело себя первое живое тестирование — процесс
исчез мгновенно, без единого лога). Поэтому проверено более прицельно и
надёжно: throwaway-скрипт поднял ВТОРОЙ реальный `socketServer.js` (тот же
код, та же dev-БД) на отдельном порту, реальный пользователь + реальный
socket.io-клиент сделали `call:invite` (без настоящего WebRTC — не нужен,
`activeCalls` наполняется уже на этапе invite), затем напрямую вызваны
`io.getActiveCallsCount()` (0→1 после invite) и `io.notifyCallsEndingSoon()`
— клиент получил `call:ending-soon` с верным `callId`/текстом, `call:end`
после этого штатно очистил `activeCalls` обратно до 0. Это покрывает всю
НОВУЮ логику; сама доставка SIGTERM — не изменённый код, уже работавший в
проде на Linux/Docker (Amvera) до этой правки. Backend 160/160 тестов и
сборка фронта (tsc+vite) зелёные (эта фича не имеет автоматических тестов —
им нужен полноценный socket.io test harness, это относится к §10, который
пока не сделан).

## 8. [P1] Надёжность push-подписок

**Статус:** `web/src/utils/push.ts:57-60` — `registerPush()` глотает все
ошибки в `console.warn`, без retry и без индикации пользователю. Нет
обработчика `pushsubscriptionchange` в `web/src/sw.ts`.

**Проблема.** Браузеры (особенно iOS Safari) периодически инвалидируют push-
подписки. Без `pushsubscriptionchange`-листенера подписка не переоформляется
автоматически — пользователь тихо перестаёт получать любые пуши, **включая
пуши о входящих звонках**, и не узнаёт об этом, пока кто-то не пожалуется
«я тебе звонил, а у тебя не звонило».

**Объём работ:**
1. В `web/src/sw.ts` добавить `self.addEventListener('pushsubscriptionchange',
   ...)` — получить новую подписку через `pushManager.subscribe` с тем же
   `applicationServerKey` и переотправить на `/push/subscribe`

## 9. [P1] Очистка приватных данных на устройстве при logout

**Критерии приёмки:** после logout `localStorage.getItem('blizkie-drafts')`
пуст при любом из существующих путей выхода (протестировать хотя бы 2–3:

## 11. [P1] Резервный TURN-провайдер для звонков

**Статус:** один самостоятельно поднятый coturn на VDsina — единая точка
отказа (`docs/CALLS_TROUBLESHOOTING.md` документирует ~10% успеха звонков при
проблемах конфигурации/firewall, что уже устранялось точечно).

**Проблема.** Даже при полностью исправном текущем coturn — это единственный
relay. Падение сервера/провайдера, блокировка UDP-портов у части операторов,
скачок нагрузки — и звонки перестают устанавливаться у всех пользователей за
симметричным NAT одновременно, без деградации, а полным отказом.

**Объём работ:**
- Добавить второй TURN URL в конфиг ICE-серверов (`GET /calls/ice-servers`,
  судя по `CALLS_TROUBLESHOOTING.md`) — managed-провайдер (например Metered,
  уже упоминается в журнале как рассматривался) как fallback наравне с
  self-hosted coturn. WebRTC сам перебирает ICE-кандидатов от всех
  перечисленных серверов — добавление второго не требует логики выбора,
  только конфиг.
- Замерить (те же `[WebRTC][stats]`-логи, что уже добавлены в
  `webrtcManager.ts`) какой сервер реально даёт relay в проблемных сетях.

**Критерии приёмки:** при отключении/недоступности self-hosted coturn (тест
намеренным firewall-блоком) звонки продолжают устанавливаться через
резервный TURN.
