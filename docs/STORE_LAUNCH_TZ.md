## 3. [P0] Нативная обёртка: TWA (Android) + Capacitor (iOS)

**Статус: не начато.** Нет `capacitor.config.*`, нет `android/`/`ios/`, нет
зависимостей Capacitor/Cordova/Expo/React Native. Есть только корректный PWA
(`vite-plugin-pwa`, `web/src/sw.ts`, манифест в `vite.config.ts`).

**Проблема.** Без артефакта под конкретную платформу подавать в сторы
физически нечего — это не вопрос доработки кода, а отдельный build-pipeline.
Пути для Android и iOS принципиально разные по трудозатратам и рискам.

### 3.1 Android — TWA (Trusted Web Activity), рекомендуемый первый шаг

Google официально поддерживает публикацию PWA как обёрнутого TWA — это
быстрее и дешевле, чем полноценная нативная разработка.

**Объём работ:**
- Инструмент: [Bubblewrap CLI](https://github.com/GoogleChromeLabs/bubblewrap)
  или PWABuilder — генерирует Android-проект вокруг существующего манифеста.
- Обязательное условие: **Digital Asset Links** — файл
  `.well-known/assetlinks.json` на домене прод-фронта (Vercel), подтверждающий
  владение доменом связкой с SHA-256 отпечатком подписи APK/AAB — иначе TWA
  покажет браузерную строку URL сверху (провал «нативного» вида).
  Разместить статикой в `web/public/.well-known/assetlinks.json`.
- Манифест (`vite.config.ts`) уже содержит нужные поля (`name`, `icons`,
  `display: 'standalone'`, `start_url`) — переиспользуется как есть.
- Подписной ключ Android (keystore) — сгенерировать и **бережно хранить**
  (потеря = невозможность обновлять приложение в дальнейшем).
- Пуш-уведомления: TWA использует тот же Web Push API через тот же
  Service Worker — переделывать `web/src/utils/push.ts` не требуется.
- Публикация в Google Play Console: карточка, скриншоты (реальные, с
  устройства — см. раздел 12), Data Safety форма (см. закрытый раздел 1 — что
  именно собираем), возрастной рейтинг (учитывая открытый поиск пользователей
  — скорее всего Teen, не «для всех»).

**Критерии приёмки:** установленное из Play Store (внутренний тест-трек)
приложение открывается без видимой браузерной строки URL, push работает,
deep-links (`blz:`-схема — см. `web/src/deeplinks.ts`) резолвятся.

### 3.2 iOS — Capacitor, более трудоёмкий и рискованный путь

Apple не признаёт TWA-аналог; исторически отклоняет «сайт в вебвью» по
Guideline 4.2 (Minimum Functionality) без ощутимой нативности.

**Объём работ:**
- `npm install @capacitor/core @capacitor/ios`, `npx cap init`, `npx cap add
  ios` — обернуть уже собранный `web/dist` (для финального релиза Apple
  предпочитает бандлить статику внутрь ipa, а не грузить с внешнего сервера
  как основной режим — сетевые вызовы к API/сокетам остаются, это ок, но
  начальный HTML/JS должен идти из бандла).
- Полностью убрать любой намёк на browser chrome — Capacitor по умолчанию это
  делает, но перепроверить safe-area (`viewport-fit=cover` + CSS
  `env(safe-area-inset-*)` — сейчас не проверено, вероятно отсутствует под
  «чёлку»/Dynamic Island, добавить в `web/index.html`/базовые стили).
- Камера/микрофон для звонков и видео-кружков: в WKWebView `getUserMedia`
  работает, но **обязательно** нужны ключи `NSCameraUsageDescription`/
  `NSMicrophoneUsageDescription` в `Info.plist`, иначе мгновенный краш при
  первом запросе разрешения.
- Push-уведомления — **это самый большой риск.** WKWebView не имеет доступа к
  Web Push так, как в Safari PWA. Для iOS-приложения из App Store нужен
  `@capacitor/push-notifications` (APNs) — это отдельная ветка на бэкенде:
  `backend/src/utils/webPush.js`/`pushService.js` умеет только Web Push
  (VAPID); нужен параллельный APNs-путь (сертификат/ключ Apple Push, отправка
  через `node-apn` или APNs HTTP/2 API) для звонков и сообщений на iOS-сборке.
  Учитывая, что вся история звонков в журнале завязана на надёжность push
  («входящий звонок доходит через push»), это критично не упростить.
- Sign in with Apple — **не требуется**: приложение не предлагает сторонние
  OAuth-логины (только пароль + passkeys), поэтому правило 4.8 не триггерится.
- App Store Review Guidelines 5.1.1(v) — **уже выполнено**: `DELETE
  /users/me` даёт полное самостоятельное удаление аккаунта с подтверждением
  паролем (закрытый раздел 5).
- TestFlight — прогнать реальный бета-цикл перед публичным релизом.

**Критерии приёмки:** IPA проходит внутренний TestFlight-билд, входящий
звонок доставляется push-уведомлением на реальном iPhone при свёрнутом
приложении, камера/микрофон запрашиваются с понятным описанием, нет видимого
browser chrome, safe-area учтена на всех экранах с notch/Dynamic Island.

**Решение, которое нужно принять до старта:** с чего начинать — только
Android (TWA, дни-недели) с последующим iOS, или сразу оба параллельно через
Capacitor. Рекомендация: **TWA на Android первым** — даёт работающий
стор-листинг быстро и дёшево, вскрывает реальные проблемы (push, deep-links,
safe-area) на более простой платформе, прежде чем вкладываться в более
тяжёлый и рискованный iOS-путь.

## 7. [P1] Звонки переживают деплой/рестарт процесса — остаток

**✅ Пункт «минимум» сделан (2026-07-08)** — graceful shutdown: на `SIGTERM`
сервер шлёт всем участникам активных звонков `call:ending-soon` вместо
тихого обрыва, откладывает жёсткий разрыв на `CALL_SHUTDOWN_GRACE_MS` (env,
дефолт 4000мс). Подробности и как проверено — `CLAUDE.md`, запись 2026-07-08.

**Осталось (не сделано, пользователь явно отложил при первой реализации):**
не деплоить, если есть активные звонки — CI-джоб перед деплоем опрашивает
`GET /health` (расширить полем `activeCalls: N`, метод уже есть —
`io.getActiveCallsCount()`) и либо ждёт (poll с таймаутом), либо явно
предупреждает в логе деплоя. Компромисс между «блокировать деплой» и «просто
уведомить» — решить при старте задачи. Долгосрочно эта же проблема снимается
целиком переездом на Redis (раздел 16), но не стоит делать полумеру ради
этого отдельно от полного перехода.

**Критерии приёмки:** тестовый деплой во время активного звонка либо не рвёт
его резко, либо CI осознанно откладывает деплой при непустых звонках.

## 11. [P1] Резервный TURN-провайдер для звонков

**Статус: не начато.** Один самостоятельно поднятый coturn на VDsina — единая
точка отказа (`docs/CALLS_TROUBLESHOOTING.md` документирует историю
проблем с конфигурацией/firewall, уже устранявшихся точечно).

**Проблема.** Даже при полностью исправном текущем coturn — это единственный
relay. Падение сервера/провайдера, блокировка UDP-портов у части операторов,
скачок нагрузки — и звонки перестают устанавливаться у всех пользователей за
симметричным NAT одновременно, без деградации, а полным отказом.

**Объём работ:**
- Добавить второй TURN URL в конфиг ICE-серверов (`GET /calls/ice-servers`,
  `backend/src/routes/calls.js`) — managed-провайдер (например Metered) как
  fallback наравне с self-hosted coturn на VDsina. WebRTC сам перебирает
  ICE-кандидатов от всех перечисленных серверов — добавление второго не
  требует логики выбора, только конфиг.
- Замерить (те же `[WebRTC][stats]`-логи, что уже есть в `webrtcManager.ts`)
  какой сервер реально даёт relay в проблемных сетях.

**Критерии приёмки:** при отключении/недоступности self-hosted coturn (тест
намеренным firewall-блоком) звонки продолжают устанавливаться через
резервный TURN.

**Чек-лист (прогонять перед каждым релизом в сторы и после значимых

- [ ] Тёмная/светлая тема на реальном OLED (не эмулированная в DevTools).
- [ ] Работа офлайн (самолётный режим).

**Критерии приёмки:** чек-лист пройден на минимум одном реальном устройстве

## Рекомендуемый порядок выполнения (обновлено 2026-09-03)

Принцип: сначала то, что делается чистым кодом прямо сейчас (не требует
внешних аккаунтов/денег/решений пользователя), затем — что требует
внешних обязательств по нарастающей (бесплатный аккаунт → платный →
App Store/Play аккаунты → аппаратное тестирование).

1. **Чистым кодом, без внешних аккаунтов:** §7 остаток (CI не деплоит при
   активных звонках), §8 остаток (лог push-неудач в Sentry), §10 остаток
   (Playwright E2E). Можно делать в любом порядке, независимы друг от друга.
2. **Требует решения/аккаунта пользователя:**
   - §3.1 Android TWA — Google Play Console ($25 разово) + keystore.
     Рекомендованный первый шаг раздела 3 (дешевле и быстрее iOS).
   - §11 Резервный TURN — managed-провайдер (может быть платным), логично
     делать рядом с публикацией под реальных пользователей (после §3.1).
   - §3.2 iOS Capacitor — Apple Developer ($99/год) + Mac для сборки. Самый
     дорогой и рискованный путь. Начинать после того, как Android обкатан.
   - §12 QA на реальных устройствах — процесс, не разовая задача; начинать
     прогонять с первого релиза (Этап Android).
3. **Бэклог — по сигналу от роста аудитории/нагрузки, не по графику:**
   §16 Redis-адаптер, §17 Admin Panel v2 (раздел «Call success rate» из
   §17 полезно поднять пораньше — объективно измерить эффект §11).
