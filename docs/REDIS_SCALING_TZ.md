# ТЗ: горизонтальное масштабирование realtime-слоя (Redis-адаптер)

> Статус: **БЭКЛОГ «на вырост»**. Сейчас НЕ реализуем. Делать, когда появится
> реальный сигнал: рост аудитории (один процесс перестаёт справляться) или
> требование бесшовного деплоя без обрыва сокетов/звонков.

## 1. Проблема

Бэкенд работает **в одном процессе Node**, и всё состояние реального времени
живёт **в его оперативной памяти**. Запустить второй экземпляр нельзя — копии не
видят состояние друг друга: пользователь онлайн на экземпляре A будет «offline»
для тех, кто подключён к экземпляру B; звонок между ними не соединится; broadcast
`new-message` дойдёт только до части людей.

Следствия:
- **Нет горизонтального масштабирования** (один процесс — потолок нагрузки).
- **Единая точка отказа**: падение/редеплой процесса рвёт связь у всех.
- **Деплой с обрывом**: при перевыкатке все сокеты переподключаются разом.

### Что именно «в памяти» (где чинить)

`backend/src/socket/socketServer.js`:
- `onlineUsers: Map<userId, count>` — присутствие.
- `activeCalls: Map<callId, call>` — активные звонки (вся сигнализация WebRTC).
- `typingThrottle`, `callRateTracker`, `socketEventTracker` — троттлинг/лимиты.
- Комнаты socket.io `user:<id>`, `chat:<id>`, `session:<id>` — в памяти адаптера.
- `setInterval`-джобы: доставка отложенных сообщений (30с), «Вопрос дня» (60с),
  истечение presence (60с), sweep отозванных сессий (60с).

`backend/src/config/database.js`: один файл **SQLite** на томе `/data` одной
машины — отдельное ограничение (см. §6).

## 2. Цель

Сделать realtime-слой **stateless/общим**, чтобы можно было запускать N копий
бэкенда за балансировщиком (sticky-сессии не обязательны при работающем адаптере),
с корректным presence/звонками/broadcast между копиями и без дублирования
фоновых джоб.

## 3. Объём работ

### 3.1 Socket.IO Redis-адаптер (ядро)
- Зависимости: `@socket.io/redis-adapter` + `redis` (v4).
- В `initSocket(httpServer)` создать pub/sub клиентов Redis и
  `io.adapter(createAdapter(pubClient, subClient))`.
- Эффект: `io.to('chat:<id>').emit(...)` и `io.to('user:<id>').emit(...)`
  доставляются **между всеми экземплярами** через Redis pub/sub. Комнаты больше
  не «локальны» одному процессу.
- Транспорты оставить `['websocket','polling']`; при нескольких экземплярах за
  балансировщиком включить **sticky-сессии** ИЛИ убедиться, что polling-апгрейд
  идёт на тот же узел (с websocket-онли sticky не критичен, но желателен).

### 3.2 Presence (`onlineUsers`) → Redis
- Заменить `Map` на счётчики в Redis: `INCR/DECR presence:user:<id>` на
  connect/disconnect; онлайн = значение > 0.
- `user-online/user-offline` рассылать через адаптер (уже покрыто §3.1), но
  «первый сокет/последний сокет» считать по Redis-счётчику, а не по локальному.
- TTL/самоочистка: при падении экземпляра его сокеты «повиснут» — предусмотреть
  периодическую сверку (heartbeat-ключи с TTL) или подписку на disconnect.
- `io.kickSession` / sweep отозванных сессий — работает через адаптер
  (`io.in('session:<id>').disconnectSockets(true)` доставляется всем узлам).

### 3.3 Звонки (`activeCalls`) → Redis
- Перенести запись звонка в Redis-хэш `call:<id>` (callerId/calleeId/chatId/
  callType/createdAt/startedAt) + индекс «кто в звонке» `incall:user:<id>`.
- Проверки «уже в звонке», авто-эвикт зомби-звонков, серверный таймаут 90с —
  переписать на Redis (таймер можно держать на узле, владеющем звонком, либо
  через отложенный ключ + проверку).
- Сигналинг (offer/answer/ice) уже идёт через `io.to('user:<id>')` → работает
  через адаптер автоматически.

### 3.4 Троттлинг/лимиты
- `typingThrottle`/`socketEventTracker` можно оставить **локальными** (троттлинг
  на узел допустим). `callRateTracker` — желательно в Redis (иначе лимит звонков
  обходится переключением узла), но не критично на первом этапе.

### 3.5 Фоновые джобы (анти-дубликат)
- Сейчас 4 `setInterval` крутятся в процессе. При N копиях они будут срабатывать
  **N раз** → дубли сообщений/«Вопроса дня».
- Решение: **лидер-лок** через Redis (`SET job:lock NX PX <ttl>` с продлением)
  — джобы выполняет только держатель лока. Либо вынести джобы в отдельный
  one-replica «worker»-процесс/cron, а web-копии оставить только на трафик.

### 3.6 Конфиг/инфраструктура
- Env: `REDIS_URL` (вкл. адаптер только при наличии — иначе текущий
  single-process режим как fallback, чтобы dev/малый прод работал без Redis).
- Поднять Redis (Amvera-сервис/managed). Объёмы маленькие; важна низкая задержка.

## 4. План внедрения (поэтапно, обратимо)
1. Ввести `REDIS_URL` + опциональный адаптер (без переноса состояния) →
   проверить broadcast между 2 экземплярами на стенде. **Фича-флаг: нет URL =
   старое поведение.**
2. Presence → Redis (§3.2). Проверить онлайн/offline между узлами + падение узла.
3. Звонки → Redis (§3.3). Проверить звонок «через разные узлы».
4. Лидер-лок для джоб (§3.5). Проверить отсутствие дублей при 2 копиях.
5. Включить ≥2 реплик в проде + балансировщик (sticky при необходимости).

## 5. Риски и нюансы
- **Сложность отладки** распределённого состояния (гонки presence/звонков).
- **Redis — новая зависимость** (стоимость, доступность; падение Redis = деградация
  realtime → нужен graceful fallback и алёрты).
- **Sticky-сессии** на балансировщике для polling-апгрейда.
- Зомби-сокеты при падении узла (TTL-heartbeat обязателен).

## 6. Смежное: SQLite → сетевая БД (отдельное ТЗ при необходимости)
Redis решает realtime, но запись данных всё ещё в **одном SQLite-файле** на
одной машине. Для настоящего масштабирования записи (много экземпляров,
надёжность, бэкапы без простоя) в какой-то момент потребуется миграция на
**PostgreSQL**. Это БОЛЬШЕ по объёму, чем Redis-адаптер, и делается отдельно —
здесь не покрывается. До этого порога один SQLite + текущие бэкапы достаточны.

## 7. Критерии приёмки
- 2+ экземпляра за балансировщиком: presence/«печатает»/`new-message`/звонки
  работают между пользователями на **разных** узлах.
- Отложенные сообщения и «Вопрос дня» доставляются **ровно один раз** при N копиях.
- Падение одного экземпляра не рвёт связь у пользователей других экземпляров.
- Без `REDIS_URL` поведение идентично текущему (single-process).

## 8. Когда делать
Не раньше, чем появится одно из: (а) один процесс упирается в CPU/память под
реальной нагрузкой; (б) нужен деплой без обрыва сокетов/звонков; (в) требуется
отказоустойчивость (несколько реплик). Для аудитории «семья/друзья» — преждевременно.
